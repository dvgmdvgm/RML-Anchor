## Основные команды

Эти четыре команды — ядро системы. Они покрывают базовый цикл работы: начал сессию → работаешь → сохраняешь знания → ищешь знания → завершил сессию.

## 1. `/wakeup` — Пробуждение

### Зачем существует

Каждый AI-ассистент начинает сессию с чистого листа. Он не знает ни вашего проекта, ни прошлых решений, ни текущих задач. `/wakeup` решает эту проблему: он загружает контекст, восстанавливает состояние и возвращает AI «в курс дела».

Это как утренний брифинг для коллеги, который вернулся из отпуска. Вместо того чтобы вы сами рассказывали ему обо всём — он читает журнал и возвращается в работу самостоятельно.

### Когда вызывать

- **В начале каждой новой сессии** с AI
- **При смене чата** (новый диалог в IDE)
- **После длительного перерыва** в работе

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         │
         │  Читает .agent/memory/13_preferences/language.md
         │  Определяет язык: ru, en, es, de...
         │  ВСЯ дальнейшая работа идёт на этом языке
         ▼
Шаг 2: Загрузка главного индекса
         │
         │  Читает .agent/MEMORY_INDEX.md
         │  Получает карту всех 13 категорий
         │  Видит, сколько записей и когда обновлялись
         ▼
Шаг 3: Проверка незавершённой сессии
         │
         │  Читает .agent/memory/07_context/current_session.md
         │  Если там есть данные (не шаблон) — это значит,
         │  что прошлая сессия НЕ была завершена через /sleep
         │
         ├── Данные есть? → Архивирует как "orphan" сессию
         │                   и предупреждает пользователя
         └── Пусто? → Продолжает нормально
         ▼
Шаг 4: Загрузка истории сессий
         │
         │  Читает последние 2-3 файла из
         │  .agent/memory/07_context/session_history/
         │  Извлекает: темы, решения, заметки
         ▼
Шаг 5: Проверка незавершённых задач
         │
         │  Читает .agent/memory/07_context/pending_tasks.md
         │  Показывает задачи с приоритетами
         ▼
Шаг 6: Загрузка предпочтений
         │
         │  Читает стиль кодирования, коммуникации
         │  Применяет к своему поведению
         ▼
Шаг 7: Инициализация новой сессии
         │
         │  Обновляет current_session.md
         │  Устанавливает статус: Активна
         ▼
Шаг 8: Отчёт пользователю
         │
         └── Выводит: статистику, прошлые решения,
             незавершённые задачи, готовность к работе
```

### Почему была добавлена

Без этой команды каждая сессия начинается «с нуля». Пользователь тратит 15–20 минут на повторное объяснение контекста. `/wakeup` автоматизирует этот процесс и сокращает время до нескольких секунд.

### Пример использования

```
Пользователь: /wakeup

AI: 🚀 Загружаю контекст проекта...

    ✅ Сессия начата!
    
    📊 Память проекта:
    | Параметр | Значение |
    |----------|----------|
    | Категорий | 13 |
    | Записей | 15 |
    | Последняя сессия | 2026-02-06 |
    
    📅 Прошлая сессия (2026-02-06):
    | Тема | Решение |
    |------|---------|
    | Архитектура | 5-слойная модель |
    | Хранение | Markdown файлы |
    
    📌 Незавершённые задачи:
    | Приоритет | Задача |
    |-----------|--------|
    | 🔴 | Исправить CORS баг |
    
    💡 Чем займёмся сегодня?
```

## 2. `/sleep` — Завершение сессии

### Зачем существует

Если `/wakeup` — это загрузка контекста, то `/sleep` — его сохранение. Без этой команды вся работа текущей сессии — обсуждения, решения, находки — просто исчезнет. `/sleep` фиксирует всё, что произошло, и сохраняет в историю.

Это как журнал рабочего дня, который автоматически заполняется и убирается на полку — чтобы завтра можно было его открыть и вспомнить, где остановились.

### Когда вызывать

- **В конце рабочей сессии** (перед закрытием диалога)
- **Перед длительным перерывом**
- **Перед сменой AI-модели** (перед `/handoff`)
- **Когда нужно зафиксировать прогресс** промежуточно

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         │
         └── Определяет язык для архивации
         ▼
Шаг 2: Суммаризация сессии
         │
         │  AI анализирует весь текущий диалог и создаёт:
         │  - Список обсуждённых тем
         │  - Принятые решения
         │  - Список изменённых файлов
         │  - Важные заметки
         ▼
Шаг 3: Архивация в историю
         │
         │  Генерирует имя файла: session_YYYY-MM-DD_HH-MM.md
         │  Сохраняет в .agent/memory/07_context/session_history/
         ▼
Шаг 4: Обновление pending_tasks.md
         │
         │  Новые незавершённые задачи → добавляет
         │  Завершённые задачи → перемещает в "Recently Completed"
         ▼
Шаг 5: Сброс current_session.md
         │
         │  Перезаписывает пустым шаблоном
         │  Следующая сессия начнётся чисто
         ▼
Шаг 6: Обновление индексов
         │
         │  Если в других категориях создавались новые записи
         │  → обновляет их _index.md файлы
         ▼
Шаг 7: Отчёт пользователю
         │
         └── Показывает статистику и задачи на следующий раз
```

### Почему была добавлена

Без архивации сессий каждый день начинается с нуля. С ней — каждый последующий `/wakeup` загружает всё больше контекста. Память **накапливается**, а не теряется.

### Пример использования

```
Пользователь: /sleep

AI: 📝 Суммаризирую сессию...

    ✅ Сессия завершена!
    
    📊 Сегодня:
    | Показатель | Значение |
    |------------|----------|
    | Длительность | ~3 часа |
    | Решений записано | 2 |
    | Файлов изменено | 8 |
    
    📁 Архивировано:
    session_history/session_2026-02-07_17-30.md
    
    📌 На следующий раз:
    | Приоритет | Задача |
    |-----------|--------|
    | 🔴 | Доделать авторизацию |
    | 🟡 | Написать тесты |
    
    👋 До встречи!
```

## 3. `/remember` — Запоминание

### Зачем существует

В процессе работы постоянно генерируются важные знания: решения об архитектуре, найденные баги и их решения, правила бизнес-логики, конфигурации API. Без `/remember` эти знания существуют только в текущем окне чата и исчезают после закрытия.

`/remember` — это команда «запиши это навсегда». Она не просто копирует текст в файл — она **анализирует**, **категоризирует** и **структурирует** информацию, сохраняя её в правильную категорию памяти.

### Когда вызывать

- **Приняли важное решение** (какую базу данных выбрали и почему)
- **Нашли и исправили баг** (чтобы в следующий раз не тратить время)
- **Обнаружили нюанс** бизнес-логики (правило, которое легко забыть)
- **Настроили внешний API** (ключи, эндпоинты, особенности)
- **Хотите зафиксировать** любую информацию для будущих сессий

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         │
         └── Запись будет на языке пользователя
         ▼
Шаг 2: Определение категории
         │
         │  Если пользователь указал:
         │    /remember decisions мы выбрали PostgreSQL
         │    → Категория: 03_decisions
         │
         │  Если не указал:
         │    /remember нашли баг с CORS
         │    AI сам определяет → 06_problems
         │
         │  Таблица автоопределения:
         │  ┌─────────────────────────────────────────┐
         │  │ Контекст            → Категория         │
         │  │─────────────────────────────────────────│
         │  │ решение, выбор      → 03_decisions      │
         │  │ баг, ошибка, фикс   → 06_problems       │
         │  │ функция, класс, API → 05_code            │
         │  │ внешний API         → 09_external        │
         │  │ план, идея, TODO    → 12_roadmap         │
         │  │ предпочтение        → 13_preferences     │
         │  └─────────────────────────────────────────┘
         ▼
Шаг 3: Чтение индекса категории
         │
         │  Открывает _index.md выбранной категории
         │  Проверяет: есть ли уже запись по этой теме?
         ▼
Шаг 4: Создание или обновление файла
         │
         │  Новая тема → создаёт файл по шаблону _template.md
         │  Существующая → обновляет существующий файл
         ▼
Шаг 5: Обновление индекса
         │
         │  Добавляет новый файл в таблицу _index.md
         ▼
Шаг 6: Подтверждение
         │
         └── ✅ Записано в memory/03_decisions/ADR-004-postgresql.md
```

### Почему была добавлена

Человеческая память ненадёжна. AI-память — отсутствует между сессиями. `/remember` создаёт **третью память** — внешнюю, персистентную, категоризированную. Это гарантирует, что ни одно важное решение не будет потеряно.

### Пример использования

```
Пользователь: /remember Решили использовать JWT для авторизации,
              потому что нужна stateless архитектура и горизонтальное
              масштабирование. Session-based отклонили из-за проблем
              с балансировщиком.

AI: 📝 Анализирую контент...
    → Категория: 03_decisions (архитектурное решение)
    → Создаю: ADR-004-jwt-auth.md
    
    ✅ Записано в memory/03_decisions/ADR-004-jwt-auth.md
    
    Содержание:
    | Параметр | Значение |
    |----------|----------|
    | Решение | JWT для авторизации |
    | Обоснование | Stateless, масштабирование |
    | Отклонено | Session-based (балансировщик) |
```

## 4. `/recall` — Воспоминание

### Зачем существует

Какой смысл в памяти, если нельзя быстро найти нужное? `/recall` — это команда поиска по всей сохранённой памяти. Она находит решения, баги, архитектурные заметки, бизнес-правила — всё, что было сохранено через `/remember` или запишено автоматически.

Это как поисковик по вашей корпоративной базе знаний, только с пониманием контекста и естественного языка.

### Когда вызывать

- **«Почему мы выбрали PostgreSQL?»** — найдёт ADR с обоснованием
- **«Как мы решили баг с CORS?»** — найдёт описание и решение
- **«Какие API ключи у Stripe?»** — найдёт конфигурацию
- **«Что обсуждали на прошлой неделе?»** — найдёт историю сессий
- Любой вопрос к прошлым знаниям

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         ▼
Шаг 2: Анализ запроса
         │
         │  Извлекает ключевые слова из вопроса пользователя
         │  Определяет, в каких категориях искать:
         │
         │  "почему выбрали PostgreSQL?" → 03_decisions
         │  "баг с авторизацией"         → 06_problems
         │  "API Stripe"                 → 09_external
         │  "что обсуждали вчера?"       → 07_context
         ▼
Шаг 3: Чтение индексов категорий
         │
         │  Для каждой релевантной категории читает _index.md
         │  Находит файлы, подходящие по описанию
         ▼
Шаг 4: Извлечение информации
         │
         │  Читает найденные файлы
         │  Извлекает релевантные секции
         ▼
Шаг 5: Формирование ответа
         │
         │  Синтезирует ответ из найденных данных
         │  Указывает источники (путь к файлу, дату)
         │
         └── Если ничего не найдено → предлагает сохранить
```

### Почему была добавлена

Без поиска по памяти пользователь должен вручную открывать файлы, помнить имена, искать в папках. `/recall` превращает память из пассивного хранилища в **активного помощника**, который мгновенно доставляет нужную информацию.

### Пример использования

```
Пользователь: /recall как мы решили проблему с Google OAuth?

AI: 📁 Найдено в памяти:

    Источник: memory/06_problems/PROB-003-google-oauth.md
    Дата: 2026-01-20
    
    > Проблема: redirect_uri использовал http вместо https.
    > Браузер блокировал редирект из-за mixed content.
    >
    > Решение: Изменили URI в Google Cloud Console на https://
    > и добавили проверку протокола в settings.py
    
    Затронутые файлы: settings.py, config.py
```

## 5. `/anchor_agent` — Установка в проект

### Зачем существует

RLM-Anchor нужно установить в каждый проект, где вы хотите использовать персистентную память. Но у проекта уже может быть папка `.agent/` с конфигурациями IDE, другими workflow, правилами. `/anchor_agent` **безопасно** интегрирует систему, не ломая существующую структуру.

Кроме того, многие IDE используют собственные файлы правил: `GEMINI.md`, `.cursorrules`, `.windsurfrules`. Эта команда автоматически **находит и импортирует** данные из таких файлов в структуру RLM-памяти, чтобы всё было в одном месте.

### Когда вызывать

- **Один раз при первой установке** RLM-Anchor в новый проект
- **При миграции** между IDE (данные из правил IDE будут импортированы)
- **После клонирования проекта** с уже установленным RLM-Anchor

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         ▼
Шаг 2: Поиск файлов правил IDE
         │
         │  Сканирует корень проекта на наличие:
         │  GEMINI.md, .cursorrules, .windsurfrules,
         │  .github/copilot-instructions.md, CLAUDE.md...
         │
         │  Если нашёл → парсит и готовит для импорта
         ▼
Шаг 3: Импорт правил IDE
         │
         │  Распределяет данные по категориям:
         │  ┌──────────────────┬──────────────────────┐
         │  │ Стиль кодирования → 13_preferences/     │
         │  │ Техстек           → 01_project/          │
         │  │ Бизнес-правила    → 04_domain/           │
         │  │ Архитектура       → 02_architecture/     │
         │  └──────────────────┴──────────────────────┘
         ▼
Шаг 4: Сканирование .agent/
         │
         │  Проверяет, какие файлы уже существуют
         │  Составляет отчёт о конфликтах
         ▼
Шаг 5: Предложение вариантов
         │
         │  1. SAFE — только неконфликтующие файлы
         │  2. MERGE — слияние с существующими
         │  3. FULL — полная установка (с бэкапом)
         │  4. CANCEL — отмена
         ▼
Шаг 6: Выполнение выбранного варианта
         │
         │  Создаёт структуру:
         │  .agent/memory/ (13 категорий)
         │  .agent/MEMORY_INDEX.md
         │  .agent/skills/MEMORY_SKILL.md
         │  .agent/workflows/ (все команды)
         ▼
Шаг 7: Валидация
         │
         │  Проверяет: все файлы созданы?
         │  Индексы корректны? Язык установлен?
         ▼
Шаг 8: Отчёт (включая импорт правил IDE)
         │
         └── Показывает: что создано, что импортировано,
             рекомендует удалить оригиналы файлов правил IDE
```

### Почему была добавлена

Пользователи работают в разных IDE с разными конфигурациями. Нельзя просто «скопировать папку» — это может сломать их настройки. `/anchor_agent` — это **безопасный установщик**, который анализирует ситуацию, предупреждает о конфликтах и даёт выбор.

Импорт правил IDE — потому что информация не должна дублироваться. Если у пользователя уже есть `GEMINI.md` с правилами — зачем держать их отдельно от системы памяти?

## 6. `/anchor_briefing` — Полный брифинг

### Зачем существует

Иногда нужен **полный обзор** всего, что система знает о проекте. Не фрагментарно (как `/recall`), а целиком — от описания проекта до планов на будущее. Это like executive summary, но автоматически генерируемый из реальных данных памяти.

### Когда вызывать

- **При онбординге** нового члена команды (или новой AI-модели)
- **После длительного перерыва** в работе (недели/месяцы)
- **Для аудита знаний** — что система знает, а что нет
- **Перед стратегическими решениями** — нужна полная картина

### Как работает внутри

```
Шаг 1: Чтение языковых настроек
         ▼
Шаг 2: Последовательное сканирование ВСЕХ 13 категорий
         │
         │  Для каждой категории:
         │  1. Читает _index.md
         │  2. Если есть контент → читает ключевые файлы
         │  3. Если пусто → отмечает "Нет записей"
         ▼
Шаг 3: Генерация полного отчёта
         │
         │  Формирует структурированный документ со ВСЕМИ
         │  13 секциями: проект, архитектура, решения, домен,
         │  код, проблемы, контекст, люди, внешние интеграции,
         │  тестирование, деплоймент, roadmap, настройки
         ▼
Шаг 4: Добавление статистики
         │
         └── Сводная таблица: сколько записей в каждой категории
```

### Почему была добавлена

Это **самая тяжёлая** команда в системе — она читает всё. Но именно поэтому она самая ценная для ситуаций, когда нужна полная картина. Без неё пользователь должен вручную открывать все 13 категорий и читать каждый файл.

## 7. `/memory-stats` — Статистика

### Зачем существует

Быстрый способ узнать состояние системы памяти, не читая все файлы. Сколько записей? Какие категории заполнены? Что пусто? Когда последний раз обновлялись данные?

### Когда вызывать

- **Для быстрой проверки** состояния памяти
- **После серии `/remember`** — убедиться, что всё сохранилось
- **Для оценки** заполненности — какие категории требуют внимания

### Как работает внутри

Простая команда: проходит по всем 13 категориям, считает файлы (исключая `_index.md` и `_template.md`), собирает даты последнего обновления и выводит сводную таблицу с рекомендациями.

### Почему была добавлена

Иногда не нужен полный брифинг — нужна просто цифра. «Сколько записей?», «Что пусто?». `/memory-stats` отвечает за секунды.

### Пример использования

Пользователь: /memory-stats

## 8. `/anchor_backup` — Резервное копирование

### Зачем существует

Память ценна. Потерять месяцы накопленных знаний из-за случайного `rm -rf` или сбоя диска — недопустимо. `/anchor_backup` создаёт полный ZIP-архив всей системы памяти.

Важная деталь: бэкап включает **только файлы RLM-Anchor** (строгий список). Ваши собственные конфигурации IDE в `.agent/` не затрагиваются и не попадают в архив. Это защищает приватность и уменьшает размер бэкапа.

### Когда вызывать

- **Перед крупными изменениями** в проекте
- **Перед очисткой** (`/anchor_cleanup`)
- **Для переноса** проекта на другой компьютер
- **Периодически** для страховки (раз в неделю)

### Как работает внутри

Создаёт ZIP-архив строго определённых файлов (13 категорий памяти, скрипты, skills, workflows, индекс) в папку `.agent/backups/` с именем `anchor_backup_YYYY-MM-DD_HH-MM.zip`. Автоматически удаляет старые бэкапы, если их больше 5 (настраивается).

### Почему была добавлена

Любая система хранения данных должна иметь механизм резервного копирования. Это базовая инженерная дисциплина.

---

## 9. `/anchor_restore` — Восстановление

### Зачем существует

Обратная операция: восстановить систему из бэкапа. Работает при переносе на другой компьютер, откате к предыдущему состоянию или после аварии.

### Когда вызывать

- **При переносе** проекта на другой компьютер
- **Для отката** к предыдущему состоянию
- **После случайного удаления** файлов
- **При миграции** между IDE

### Как работает внутри

```
Шаг 1: Валидация ZIP-файла
         │
         │  Проверяет: существует? Правильная структура?
         │  Содержит memory/, workflows/, MEMORY_INDEX?
         ▼
Шаг 2: Проверка существующей установки
         │
         │  Если .agent/ уже существует → предлагает:
         │  1. Перезаписать (с бэкапом текущего)
         │  2. Слить (merge)
         │  3. Отменить
         ▼
Шаг 3: Создание safety-бэкапа текущего состояния
         │
         │  pre_restore_backup_YYYY-MM-DD_HH-MM.zip
         ▼
Шаг 4: Извлечение архива
         ▼
Шаг 5: Верификация восстановления
         │
         └── Проверяет ключевые файлы → отчёт
```

### Почему была добавлена

`/anchor_backup` без `/anchor_restore` бесполезен. Это парная команда: backup создаёт копию, restore восстанавливает из неё.

## 10. `/anchor_cleanup` — Умная очистка

### Зачем существует

Со временем память растёт. Старые сессии накапливаются, устаревшие проблемы занимают место, дубликаты появляются. Без очистки коэффициент релевантности (R) падает — AI тратит больше контекста на чтение неактуальных данных.

`/anchor_cleanup` — не тупое удаление. Это **интеллектуальная очистка** с системой скоринга, TTL, суммаризацией и безопасными бэкапами.

### Когда вызывать

- **Раз в месяц** для профилактики
- **Когда `/memory-stats` показывает** много записей
- **Если AI стал медленнее** загружать контекст
- **Перед важной фазой** проекта (очистить устаревшее)

### Как работает внутри

```
Шаг 1: Загрузка настроек очистки
         │
         │  Из .agent/memory/13_preferences/cleanup_settings.md
         │  TTL по категориям, пороги скоринга, действия
         ▼
Шаг 2: Сканирование всех файлов
         │
         │  Для каждого: дата создания, размер, категория
         ▼
Шаг 3: Расчёт скора важности
         │
         │  Importance = BASE_WEIGHT[category]
         │             × RECENCY_FACTOR
         │             × ACCESS_FACTOR
         │             × EXPLICIT_BOOST
         │
         │  Категоризация файлов:
         │  🟢 KEEP     (Score > 0.7)   — не трогать
         │  🟡 REVIEW   (Score 0.4-0.7) — спросить пользователя
         │  🟠 SUMMARIZE (старые сессии) — объединить в дайджест
         │  🔴 ARCHIVE  (Score 0.2-0.4) — переместить в архив
         │  ⚫ DELETE   (Score < 0.2)   — удалить (с бэкапом)
         ▼
Шаг 4: Показ отчёта пользователю
         │
         │  Детальная таблица по каждому действию
         │  Пользователь подтверждает или отменяет
         ▼
Шаг 5: Выполнение
         │
         │  ✓ Суммаризация: 8 сессий → 1 дайджест
         │  ✓ Архивация: перемещение в .agent/archive/
         │  ✓ Удаление: с автоматическим бэкапом
         ▼
Шаг 6: Отчёт о результатах
```

### Почему была добавлена

Система без обслуживания деградирует. `/anchor_cleanup` — это **сборщик мусора** для памяти. Он гарантирует, что память остаётся эффективной и релевантной, а не превращается в свалку устаревших данных.

## 11. `/anchor_remove` — Удаление системы

### Зачем существует

Если пользователь решил, что RLM-Anchor больше не нужен, он должен иметь возможность **чисто удалить** систему. Но удаление должно быть безопасным: с подтверждением, с бэкапом, с сохранением нерелевантных файлов.

### Когда вызывать

- **Когда решили отказаться** от системы памяти
- **При полной переустановке** (удалить → установить заново)
- **Крайне редко** — это деструктивная команда

### Как работает внутри

```
Шаг 1: Предупреждение ⚠️
         │
         │  Показывает, что будет удалено
         │  Подтверждает: ваши IDE-конфиги НЕ затронуты
         ▼
Шаг 2: Двухфакторное подтверждение
         │
         │  Генерирует случайный код (8 символов)
         │  Пользователь должен ввести его вручную
         │  Это защита от случайного вызова
         ▼
Шаг 3: Автоматический бэкап
         │
         │  Создаёт anchor_backup_FINAL_YYYY-MM-DD.zip
         │  Прежде чем удалить хоть один файл
         ▼
Шаг 4: Удаление строго по списку
         │
         │  Удаляет ТОЛЬКО файлы RLM-Anchor
         │  Ваши кастомные конфиги в .agent/ сохраняются
         │
         │  После удаления: пустые папки удаляются через rmdir
         │  (если не пустые — не удаляются, ваши файлы на месте)
         ▼
Шаг 5: Подтверждение
         │
         └── Показывает: что удалено, где бэкап
```

### Почему была добавлена

**Этика**: если пользователь установил систему, он должен иметь возможность полностью её удалить. **Безопасность**: удаление по строгому списку, а не `rm -rf .agent/`, который может убить конфиги IDE. **Страховка**: двойное подтверждение + обязательный бэкап.

## 12. `/handoff` — Передача контекста

### Зачем существует

Разработчики часто переключаются между AI-моделями. В одном IDE — Claude, в другом — Gemini, в третьем — GPT-4. Каждое переключение — потеря контекста. `/handoff` создаёт **компактную сводку** текущего состояния, которую можно передать другой модели.

Это как передача смены: уходящий специалист оставляет записку для следующего.

### Когда вызывать

- **Перед переключением** на другую AI-модель
- **Перед передачей проекта** другому разработчику
- **Для фиксации** текущего состояния в компактном виде

### Как работает внутри

Собирает из памяти: текущую задачу, последние решения, ключевые файлы, предпочтения, язык. Формирует **одностраничную сводку**, которую следующая модель может прочитать и мгновенно войти в курс дела.

### Почему была добавлена

AI-агностичность — один из принципов проекта. Если система работает с любой моделью, ей нужен механизм передачи контекста между моделями.

### Пример использования

```
Пользователь: /handoff

AI: # 🔄 Сводка для передачи контекста

    > Дата: 2026-02-07 18:00
    > Язык: Русский (ru)

    ## 📍 Текущее состояние
    
    Проект: AnchorGravity Memory System
    Работаем над: Документацией команд
    Последнее действие: Создан COMMANDS.md
    Следующий шаг: Ревью документации
    
    ## ⚖️ Недавние решения
    
    1. JWT для авторизации — stateless архитектура
    2. PostgreSQL — нужны транзакции
    
    ## ⚠️ Важные заметки
    
    - НЕ делать git commit/push без явного запроса
    - Язык: ВСЕ ответы на русском
    
    ## 🚀 Следующей модели:
    1. Прочитай эту сводку
    2. Проверь language.md (ru)
    3. Продолжи ревью COMMANDS.md
```

## 13. `/walkthrough` — Документация фич

### Зачем существует

После реализации фичи, исправления бага или выполнения значительной работы полезно задокументировать: что было сделано, как это работает, какие файлы изменены. `/walkthrough` автоматически генерирует такую документацию.

Это как отчёт о проделанной работе, но который пишет AI на основе реальных изменений.

### Когда вызывать

- **После завершения** крупной фичи
- **После исправления** сложного бага
- **Когда хочется зафиксировать** как что-то работает
- AI может **сам предложить** создать walkthrough после значительной работы

### Как работает внутри

Анализирует текущую сессию: какие файлы были созданы/изменены, какие решения приняты, какие паттерны использованы. Генерирует структурированный документ с описанием, примерами кода и ссылками на файлы. Сохраняет в `.agent/memory/07_context/walkthroughs/`.

### Почему была добавлена

Через неделю уже сложно вспомнить детали реализации. Через месяц — практически невозможно. `/walkthrough` создаёт **документацию по горячим следам**, пока AI ещё помнит все детали.

## Заключение

13 команд покрывают полный жизненный цикл работы с персистентной памятью:

| Этап | Команды | Цель |
|------|---------|------|
| **Установка** | `/anchor_agent` | Один раз — интеграция в проект |
| **Ежедневная работа** | `/wakeup`, `/sleep`, `/remember`, `/recall` | Основной цикл |
| **Аналитика** | `/anchor_briefing`, `/memory-stats` | Обзор и статистика |
| **Обслуживание** | `/anchor_backup`, `/anchor_restore`, `/anchor_cleanup`, `/anchor_remove` | Жизненный цикл |
| **Контекст** | `/handoff`, `/walkthrough` | Передача и документация |

Каждая команда существует по обоснованной причине. Ни одна не дублирует другую. Убери любую — и в системе появится функциональный пробел.
